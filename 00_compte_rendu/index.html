02 · Point de départ

          
Tests des modèles bruts

          

            Résultats figés sur les 2 147 requêtes du jeu de test, avant
            fine-tuning. Les meilleurs résultats Qwen sont indiqués en vert ;
            GPT-5.6 Luna est présenté comme repère externe.
          

        

        

          
    
            
  • 
              Execution accuracy : part des requêtes dont le résultat
              renvoyé par SQLite est exactement le même que celui de la requête
              de référence. C’est la mesure principale de la justesse
              fonctionnelle.
            
    • 
            
  • 
              Exact match : part des requêtes dont le texte SQL, après
              normalisation, est identique à la référence. Une requête
              différente mais équivalente peut donc réussir l’exécution sans
              compter ici.
            
    • 
            
  • 
              SQL exécutable : part des requêtes que SQLite peut lancer
              sur la base concernée sans produire d’erreur. Cela vérifie
              notamment que les tables, colonnes et types employés sont
              cohérents avec le schéma.
            
    • 
            
  • 
              SQL valide : part des sorties dont la syntaxe peut être
              analysée comme du SQL. Cette métrique ne garantit ni que les noms
              du schéma existent, ni que la réponse à la question est correcte.
            
    • 
            
  • 
              Erreurs d’exécution : requêtes syntaxiquement valides, mais
              rejetées au moment de l’exécution — par exemple à cause d’une
              table ou d’une colonne inexistante.
            
    • 
            
  • 
              SQL invalides : sorties qui ne peuvent pas être analysées
              comme une requête SQL, souvent en raison d’une syntaxe incomplète,
              d’un format parasite ou d’une réponse en langage naturel.
            
    • 
            
  • 
              Timeouts : exécutions interrompues parce qu’elles dépassent
              la durée autorisée, généralement à cause d’une requête trop
              coûteuse.
            
    •

04 · Optimisation LoRA

          
Explorer les paramètres du Qwen 3.5 2B

          

            Le Qwen 3.5 2B réagit particulièrement bien au fine-tuning : son
            execution accuracy test passe de 29,48 % à 67,44 % (+37,96 points).
            Nous allons donc tester différentes configurations LoRA sur ce
            modèle. Pour isoler l’effet des hyperparamètres, les mêmes données
            et le même protocole d’évaluation sont conservés : seule la
            configuration LoRA varie.
          

        

        

          
04.1 · Capacité des adaptateurs

          
Faire varier r et α à ratio constant

          

            Nous faisons varier le rang r et le facteur d’échelle
            α, tout en conservant α / r = 2. Le
            dropout et tous les autres paramètres d’entraînement restent
            inchangés.

          1 034 exemples de validation :

          plus légères produisent des résultats très proches. Nous retenons donc

          suite des essais.

05 · Data scaling

          
Mesurer l’effet du volume de données

          

            Après avoir fixé une configuration LoRA compacte, nous allons
            maintenant mesurer l’apport de données d’entraînement
            supplémentaires. L’objectif est d’identifier comment l’Execution
            Accuracy évolue lorsque la taille du jeu de train augmente. Chaque
            version sera évaluée sur le même jeu de validation,
            avec le même protocole d’évaluation.
          

        

        

          Configuration conservée : Qwen 3.5 2B · LoRA
          (r=8, α=16) · learning rate
          1e-4 · 3 époques.
        

        

          Le jeu d’entraînement sera découpé en quatre volumes :
          25 %, 50 %, 75 % et
          100 %. Les sous-ensembles seront imbriqués (25% ⊂ 50% ⊂ 75% ⊂ 100%) et construits par échantillonnage contrôlé selon les
          db_id et la difficulté Spider (easy,
          medium, hard, extra) : chaque
          base et chaque niveau de difficulté y contribueront
          proportionnellement à leur nombre d’exemples. Cela permet de conserver
          une diversité raisonnablement représentative des bases, schémas et
          requêtes à chaque niveau.
        

        

          Spider ne fournit pas directement ces niveaux de difficulté dans ses
          fichiers train. Ils sont recalculés à partir de l’AST SQL gold avec
          les règles de son évaluateur officiel, qui classe chaque requête en
          easy, medium, hard ou
          extra.

06 · Qualité et diversité

          

            Ajouter des données d’entraînement, oui mais lesquelles ?
          

          

            Le data scaling montre qu’augmenter le volume améliore les
            résultats, mais que chaque lot supplémentaire apporte un gain plus
            faible que le précédent. La prochaine étape n’est donc pas seulement
            d’ajouter des exemples : il faut choisir ceux qui complètent le
            mieux ce que le modèle sait déjà faire.
          

        

        

          Commençons d’abord par regarder où notre modèle fait le plus
          d’erreurs.
        

        

          Le run entraîné sur 100 % des données est évalué sur les 1 034

          les règles de l’évaluateur officiel Spider.

Générer et contrôler les nouveaux datasets A à D

Pipeline de création des nouvelles données d’entraînement

        

          

            01
            

              Idée générale : On souhaite 5 000 nouveaux
              exemples par dataset. On prévoit quelques erreurs, soit des
              exemples créés par le modèle mais invalides soit des exemples
              valides mais dont Spider ne reconnaît pas la difficulté, donc on
              en demande 25% en plus pour arriver à un batch demandant 6 250
              exemples pour un dataset donné. Chaque prompt fournit au modèle :
            

            
    
              
  • 
                le schéma SQL (obtenu à partir de SQLite directement) de la base
                concernée
              
    • 
              
  • une consigne propre à chaque niveau de difficulté
    • 
              
  • 
                un nombre de paires à fournir (question FR - requête SQL
                associée)
              
    • 
            

            

              Des subtilités s’appliquent ensuite aux différents datasets :
            

            

              

                Dataset A
                

                  On conserve les 146 bases initiales. On veut garder la même
                  proportion d'exemples par base et la même proportion de
                  difficulté Spider intra-base.


                  Exemple : si la base 1 représente 10% des exemples du train
                    set initial et que dans ces 10% on trouve 50% d'exemples de
                    difficulté easy, 30 % de
                    hard et 10 % chacun de
                    medium et extra, on lui demandera
                    625 nouveaux exemples (10 % du Batch de 6 250),
                    distribués dans les mêmes proportions.
                  


                  Après les contrôles, les candidats valides sont conservés
                  dans l’ordre consolidé des réponses, jusqu’à
                  remplir exactement chaque quota base × difficulté
                  ; il n’y a pas de classement supplémentaire.
                

              

              

                Dataset B
                

                  On utilise les 100 nouvelles bases. Leur quota est
                  proportionnel à source_examples dans le
                  catalogue. Sans historique Spider par base, la diversité des
                  difficultés est laissée libre et mesurée après génération.

              Le script Python lit dans le catalogue le schéma SQL reconstruit
              depuis SQLite, puis l’insère sous forme de texte dans le prompt
              Batch envoyé à GPT-5.6 Luna. Le modèle produit
              alors des paires structurées question FR + SQL.
              Pour A, chaque prompt lui demande de produire un nombre exact de
              paires d’une seule difficulté Spider et lui interdit de produire
              les autres niveaux.
            

          

          

            03
            

              Les réponses brutes sont
              téléchargées et consolidées. Si la première passe
              ne suffit pas, un Batch de complément cible uniquement les quotas
              encore manquants par base et par niveau Spider. Lors de la
              production historique de A, ces passes supplémentaires ont porté
              le cumul à 10 491 paires demandées.
            

          

          

            04
            

              Le contrôle déterministe normalise le SQL, refuse
              les écritures, l’exécute sur la bonne base SQLite, élimine les
              doublons et recalcule sa difficulté avec les règles officielles de
              Spider.
            

          

          

            05
            

              Les candidats valides sont ramenés aux
              quotas exacts par base et difficulté. Pour
              A : 9 801 candidats valides parmi les

              fichier de demandes régénérable représente, lui, la première passe

            07
